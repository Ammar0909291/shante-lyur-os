C1. DEAD EVENT INFRASTRUCTURE                                     [HIGH SEVERITY]
--------------------------------------------
  noopEventBus is wired into 6 of the most critical routes:
    - createAppointment
    - rescheduleAppointment
    - createPayment
    - paymentWebhooks (×2)
    - changeUserRole

  Every domain event (AppointmentBookedEvent, PaymentCompletedEvent, etc.)
  is published and immediately discarded. The entire event-driven architecture
  is effectively disabled at the core. The communication engine works around
  this via direct function calls, but proper integration is severed.

  Files: src/app/api/appointments/route.ts
         src/app/api/appointments/[id]/reschedule/route.ts
         src/app/api/finance/payments/route.ts
         src/app/api/payments/webhooks/yookassa/route.ts
         src/app/api/payments/webhooks/robokassa/route.ts
         src/app/api/admin/users/[id]/role/route.ts


C2. SYSTEMATIC PRISMA TYPE DRIFT                             [MEDIUM-HIGH SEVERITY]
--------------------------------------------
  40+ instances of `as never`, `as unknown as`, and unsafe type casts.
  Confirmed affected files:

    payroll/calculate/route.ts       — compensationType as never (4 occurrences)
    finance/payments/route.ts        — provider as never
    payroll/compensation/route.ts    — serviceOverrides as unknown as never
    me/route.ts                      — payload as unknown as AccessPayload
    chat/users/route.ts              — ['ADMIN', ...] as never[]

  Root cause: Prisma schema was modified without regenerating TypeScript types,
  or the generated client is out of sync. TypeScript safety bypassed in all
  these locations. Runtime crashes are possible.


C3. TWO PARALLEL UI SYSTEMS                                   [MEDIUM SEVERITY]
--------------------------------------------
  src/app/(dashboard)/   — Legacy Tailwind/custom CSS shell (25 pages, active)
  src/next-ui/           — NextUI migration shell (layout only, 8 files)

  A UIVersionProvider context controls which shell renders. This creates:
    - Ongoing confusion about which system to build new features in
    - Double maintenance burden
    - Impossible UI consistency guarantees
  Neither system is finished.


C4. PERMISSION SYSTEM IS UI THEATER                           [MEDIUM SEVERITY]
--------------------------------------------
  The permissions management page (/dashboard/permissions) displays role →
  permission mappings as a static hardcoded array in the component file.

  There is NO GET /api/admin/permissions endpoint.
  No permission data is stored in or read from the database.
  The "permissions" column is pure decoration.

  The page allows ROLE CHANGES (which IS backed by DB) but the permissions
  display itself is entirely fictional.


C5. PERMISSION LOGIC BUG IN CORE BOOKING USE CASE             [HIGH SEVERITY]
--------------------------------------------
  File: src/application/use-cases/booking/create-appointment.use-case.ts
  Line: 48

  Current code:
    if (actorRole === UserRole.CLIENT && clientId !== clientId) {

  `clientId !== clientId` is ALWAYS false. This check is completely dead.
  It was intended to prevent clients from booking for other clients, but
  it never fires. Any client who knows another client's ID can book for them.


C6. MASSAGEWORKLOADOVERRIDE INCOMPLETE                         [LOW SEVERITY]
--------------------------------------------
  Two TODO comments in analytics routes reference a MassageWorkloadOverride
  table. The WorkloadOverride model exists in schema.prisma but the analytics
  routes that should read from it are stubbed.

  Files: src/app/api/analytics/dashboard/specialists/route.ts
         src/app/api/analytics/dashboard/summary/route.ts


C7. SLOTS ENDPOINT SILENT MOCK FALLBACK                       [MEDIUM SEVERITY]
--------------------------------------------
  /api/appointments/available-slots swallows database errors and returns
  mock slot data instead of a 503. A DB outage produces misleading
  availability data rather than a visible error — staff could book
  appointments based on phantom slot data.

  PHASE G — SECURITY ANALYSIS
================================================================================

CRITICAL — FIX BEFORE ANY EXTERNAL USERS TOUCH THE SYSTEM
----------------------------------------------------------

  ISSUE 1: HARDCODED JWT FALLBACKS
  Files:  src/middleware.ts:114
          src/app/api/auth/login/route.ts:17
          src/app/api/auth/register/route.ts:18
          src/app/api/auth/refresh/route.ts:8

  Current code pattern:
    const secret = process.env.JWT_SECRET ?? 'dev-access-secret-change-me';

  An attacker who knows this default (it's in the codebase) can mint valid
  JWTs for any user including SUPER_ADMIN if the env var is not set.

  Required fix:
    const secret = process.env.JWT_SECRET;
    if (!secret) throw new Error('JWT_SECRET environment variable is required');

  ─────────────────────────────────────────────────────────────────────────

  ISSUE 2: UNSIGNED PAYMENT WEBHOOKS
  Files:  src/app/api/payments/webhooks/yookassa/route.ts
          src/app/api/payments/webhooks/robokassa/route.ts

  Both Yookassa and Robokassa send HMAC signature headers with each webhook.
  Neither handler verifies these signatures. A malicious POST to either
  endpoint with a crafted body will mark appointments as paid without
  any actual payment occurring.

  Required fix: Implement HMAC-SHA256 verification using
  YOOKASSA_SECRET_KEY / ROBOKASSA_PASSWORD environment variables.


MEDIUM
------

  ISSUE 3: NO RATE LIMITING ON LOGIN
  middleware.ts sets X-RateLimit-Limit: 100 headers but no Redis-backed
  counter enforces them. /api/auth/login can be brute-forced indefinitely.

  ISSUE 4: VERBOSE INTERNAL ERROR EXPOSURE
  Dozens of routes return `error instanceof Error ? error.message : 'Unknown'`
  directly to the client. Stack traces, SQL errors, file paths can leak.

  ISSUE 5: JWT ACCESS TOKEN EXPIRY = 8 HOURS
  Standard practice is 15 minutes with silent refresh via refresh token.
  8-hour access tokens mean a compromised token is valid for a full workday.

  ISSUE 6: NO CSRF PROTECTION
  Middleware declares intent (X-CSRF-Token: required) but no route validates
  the header value.

  ISSUE 7: NO SECURITY HEADERS
  Missing CSP, X-Frame-Options, and HSTS headers in middleware responses.


LOW
---

  ISSUE 8: CLIENT SEARCH NO INPUT LENGTH LIMIT
  /api/clients/search?q= accepts unbounded strings. Prisma parameterizes them
  (no SQL injection risk) but queries can be expensive on long inputs.

  ISSUE 9: REGISTRATION ALWAYS CREATES CLIENT ROLE
  No way to register as staff via API — requires manual DB update. This is
  technically a security feature (no privilege escalation via registration)
  but means staff onboarding has no automated workflow.

  FINAL VERDICT
================================================================================

  Shante Lyur OS is a remarkably complete salon CRM prototype built with
  genuine architectural sophistication. The domain model is fully thought
  out, the infrastructure patterns are enterprise-grade, and the
  communication engine alone would justify the entire project.

  The remaining technical debt (type casts, permissions page, mock fallback)
  is real but non-blocking for an initial production launch.
